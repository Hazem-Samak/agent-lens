### 3. Required findings

**RC1 — The frozen brief's mandated regression for the npm cache/log environment override does not exist; the isolation guarantee for the four ownership queries is entirely untested.**

- Where: `Sources/AgentLensCore/Updates/NpmUpdateProbe.swift:318-336` (`npmEnvironment`), `:338-352` (`derivedScratchEnvironment`), `:996-998` (both ownership groups), `Sources/AgentLensCore/Ownership/NpmOwnershipProbe.swift:355-363` (ownership `query` passes `environment.raw`), `NpmUpdateProbe.swift:1037`, `:1072`, `:1108` (config/view/version). Tests: `Tests/AgentLensCoreTests/NpmUpdateProbeTests.swift:249-256` — `RecordingNpmRunner.run` accepts `environment` and **discards it**; a content search over `Tests/` finds **zero** `NPM_CONFIG_CACHE`/`npm_config_cache`/`NPM_CONFIG_LOGS_DIR` assertions anywhere.
- Frozen requirement: B02.5 — *“Add a regression proving all four ownership queries receive the override and no real-cache trap is touched.”* That is the initial prefix/root plus the final prefix/root pair, exactly the only npm invocations that get no `--cache/--logs-dir` flags and therefore depend solely on the environment override.
- Concrete trigger: any regression that passes the **base** environment (instead of the derived one) to `verifyWithProof`, drops a canonical assignment, or mis-handles the duplicate-removal loop at `:323-327` (which iterates `values.keys` while removing — safe today only because the `Keys` view retains storage and forces a COW copy, an unstated invariant). No test would fail, and real npm would write into the user's own npm cache/log root for the ownership and registry-config calls; the current “personal `~/.npm` unchanged” observation would silently stop holding.
- Consequence: the B02.5/AC07/AC09 isolation contract rests on one untested line of propagation. I traced the code and believe it is **correct as written**; this is a missing mandated regression, not observed misbehaviour.
- Bounded remedy (test-only, allow-listed file): one case in `NpmUpdateProbeTests` that runs a Check against the on-disk fixture with an injected environment whose `raw` contains `npm_config_cache=<sentinel>`, `NPM_CONFIG_LOGS_DIR=<sentinel>`, mixed-case `Npm_Config_Update_Notifier=1` and `TMPDIR`, using a recording runner that captures `environment` per call. Assert (a) **every** npm invocation recorded for the run — including all four ownership `prefix`/`root` calls — carries `NPM_CONFIG_CACHE` and `NPM_CONFIG_LOGS_DIR` equal to that invocation's own 0700 child under the injected base, (b) no inherited-spelling duplicate of any of the three keys survives, (c) `NPM_CONFIG_UPDATE_NOTIFIER == "false"`, (d) every child is removed and the sentinel paths are untouched. No product change is implied.

### 4. Optional observations (truly optional — not required changes, and not blockers)

1. `npm --version` is observed **per subject**, while B03.4's cost accounting names “one version query per manager/context/stage”. With two npm-source tools this issues two `--version` calls per stage. The brief explicitly says proof dedup beyond exact request deduplication is *not* required this phase, so this is a cost note only.
2. `NpmScratchBase` refuses a group/other-writable base (`NpmUpdateProbe.swift:374-390`). On macOS the default `TMPDIR` passes, and the CLI receipts prove it in a sandboxed process, but a user who sets `TMPDIR=/tmp` gets a permanent, opaque “update probe failed” for npm checks. Brief-sanctioned (“refuse symlink/unsafe root”), just worth knowing as an environment cliff.
3. The new coordinator test `admissionExpiryBeforeAnyLaunchReportsBudgetAndKeepsTheStageUsable` asserts a wall-clock window of `>= 9 && < 30` seconds; on a loaded hosted runner a 10 s sleep plus 20 s headroom is the one place I would expect flake risk in the pending exact-SHA run.
4. Evidence hygiene: the retained in-repo evidence set is excellent for tests/transport/native/CLI/matrix, but `guard21`/`packaging9` receipts for the final candidate are not retained (see §6).

### 5. Strongest objection to a PASS

The strongest challenge I could construct — and the one I would raise if forced to argue the candidate should be blocked outright — is that the npm flow's **process isolation is asserted twice at the wrong level**: once by unit tests that never observe the child environment (RC1), and once by an in-process `NSLock` plus per-process stage admission that cannot serialize a second **process** writing the same npm document. The cache document mitigates the second by design (TTL, strict revalidation, ambiguity/contamination-as-miss, validate-before-write: worst case is a lost update or an extra miss, never a false verified publish), and the frozen brief explicitly adopts that as the accepted cross-process boundary, so I do not treat it as a finding. The first, however, is not mitigated by design — it is simply unasserted — which is why RC1 stands as a required change rather than an observation.
