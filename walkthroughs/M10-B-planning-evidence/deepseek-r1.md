## Material findings

### 1. The registry-read semantics the whole eligibility policy rests on are asserted, not measured — and the frozen AC03 cannot detect the failure
**Locations:** brief B02.1 ("Use npm global mode consistently, so project `.npmrc` cannot choose the registry for a global installation"), B02.2, B02.3 ("The URL is current effective lookup routing"), B02.4 ("Do not override a custom setting with public registry"), AC03. Evidence: `/private/tmp/agent-lens-m10b-plan-b7klgulu/base.json`, `scope.json`.

**Problem.** The planner's receipts were taken with **empty** `user.npmrc` and `global.npmrc` and a cwd that contains no `package.json`. That evidence therefore cannot distinguish any of the three cases the policy depends on:
- (a) does `npm config get registry --global` still reflect a **user-level** `~/.npmrc` registry override (if `--global` restricts the read to the global npmrc, the app would report `https://registry.npmjs.org/` while the user's real npm would use a mirror, then bind `--registry=npmjs` and *override a custom setting* — explicitly forbidden by B02.4);
- (b) does `--global` exclude **project** `.npmrc` (npm derives project config from the child's cwd, and `BoundedProcessRunner` performs `posix_spawn` with **no chdir**, so the child inherits the app/CLI cwd);
- (c) does a project-level `@scope:registry` survive into `npm view` for the scoped packages this repo actually declares (`@openai/codex`, `@opencode/cli` — `Detectors/DefaultDetectors.json`). A CLI-config `--registry` does not obviously outrank a differently-named scoped config key, so a project `.npmrc` could route the metadata request to a non-npmjs host while the `--global` config read says "undefined" → the plan would accept base public, contact the wrong host, and label the result public.

Because the same command shape governs both the label and the request, a wrong assumption produces *both* a privacy/routing defect and a truthful-provenance defect, and AC03 (as written: base public, scoped public/custom, base custom + scope public, unset scope, malformed/credential, failed query, mid-flight change) cannot observe it.

**Concrete fix.** Before freeze: measure four populated-config cases — (i) user `registry=custom`, (ii) project `registry=custom` under the child cwd, (iii) user `@scope:registry=custom`, (iv) project `@scope:registry=custom` — recording argv, exit, stdout and (via a controlled transport that records hits) which host was actually contacted for `npm view … --registry=<accepted> --global`. Freeze the result into B02.1/B02.3 and add AC03 rows (ii) and (iv) with the observable: *either* zero non-npmjs metadata request *or* neutral refusal, never a "public" label with a non-npmjs request. Then pin the child context explicitly: pass `--userconfig=<derived from captured env>` and `--globalconfig=<derived>` so the read is deterministic. Note the allow-list consequence: if measurement shows `--global` alone does not exclude project config, the fix needs a spawn-cwd seam in `Sources/AgentLensCore/Process/BoundedProcessRunner.swift`, which is named in **neither** the modify list **nor** `DO NOT TOUCH` — the brief must decide this now, or the honest outcome mid-implementation is the brief's own BLOCKED stop.

### 2. B04.2's cache key ("effective non-secret query context") collides with B02.5's mandatory per-invocation random scratch root → the npm metadata cache can never hit
**Locations:** brief B04.2, B02.5, AC06; code `UpdateProbeCoordinator.swift:571` (`contextFingerprint` digests *the entire child environment* key-by-key plus the working directory) and `UpdateProbeCoordinator.swift:146-151` (`run(... cacheURL:)`).

**Problem.** The existing Homebrew precedent digests every environment pair. For npm the child environment must additionally carry the invocation-local scratch `npm_config_cache` / logs directory, which B02.5 requires to be **unique per invocation**. If the npm context digest follows the existing pattern (the natural reading of "effective query context"), every run produces a different digest, every `Check` misses, and the six-hour reuse promise in the user outcome silently never happens. An AC06 test with a *stable* injected store/scratch path would pass while production always misses.

**Concrete fix.** Replace "a stable digest of effective non-secret query context" with an **exact input list** that positively excludes invocation-local scratch/temp paths, e.g. (`"agent-lens-npm-context-v1"`, normalized accepted registry, verified package, tag, npm entry/target/fingerprint, user/global config *path identities*, session working directory), plus the explicit statement that scratch cache/log paths, `TMPDIR` and random names are excluded because they carry no routing meaning. Add an AC06 row: two consecutive Checks with **distinct** scratch roots must hit the same record (view omitted) — that is the row that would have caught this.

### 3. B03.4 misstates the existing runner bound (3 s vs measured 10 s), and the 60 s per-tool budget cannot contain the steps the brief itself mandates
**Locations:** brief B03.4 ("retain existing bounded runner limits (at most3 seconds, 1MiB output)"; "aggregate60-second monotonic budget per selected tool including final revalidation"); code `HomebrewUpdateProbe.swift:204` (`public static let queryTimeout: TimeInterval = 10`, commented "brief: ten seconds"), used by `NpmOwnershipProbe.swift:241`; `ToolDetector.swift:81` (`versionTimeout = 3`); `BoundedProcessRunner.swift:14` (1 MiB, stdout only); `UpdateCLIIntegrationTests.swift:36-38` (`cliRunBudget = 120`, comment "three 10 s manager queries").

**Problem.** Three defects in one sentence. (i) The 3 s figure appears to be `ToolDetector.versionTimeout`, not the manager query bound; the *existing* ownership/config query bound is 10 s and lives in `HomebrewUpdateProbe.swift`, which the brief forbids touching — so "retain … at most 3 s" is either a forbidden edit or an unrequested change to M9-accepted npm verification behavior. (ii) With the real 10 s bound the mandated worst case is ≈ 2×10 (initial ownership) + 2×(3–10) (base+scope config) + 20 (view) + 2×(3–10) (post-query registry re-read) + 2×10 (final full re-verification) ≈ **69–90 s > 60 s**, so a legitimate slow-but-successful run is truncated into `unknown` by design. (iii) Nothing bounds the *scan*: with k ≈ 3 npm tools the serial worst case is 3× that, which already exceeds the 120 s CLI watchdog the worker may not weaken.

**Concrete fix.** State the actual numbers per step: ownership query 10 s (unchanged, `HomebrewUpdateProbe.queryTimeout`, explicitly out of scope to change), registry config query ≤3 s (its own constant, passed per call), metadata 20 s, final re-verification 10 s×2. Then either raise the per-tool budget to ≥120 s **and** define a scan-level admission/budget, or reduce the number of full ownership passes (e.g. hoist prefix/root once per manager per scan — see finding 6) so the arithmetic closes. Correct the 3 s/10 s claim and record the resulting `cliRunBudget` value in the brief so the worker is not forced to loosen the watchdog.

### 4. B02.5's "No shared `.npm` content access" is contradicted by the ownership proof the same section requires
**Locations:** brief B02.5, B01.3/B02.1 (reuse the verifier's complete proof), B02.4 (final re-verification), AC09; code `NpmOwnershipProbe.swift:236-252` (`query` passes `environment.raw` verbatim, no cache/log override).

**Problem.** The brief concedes "npm may write its transport cache/logs even for read-only commands" and then shields only "every config/metadata invocation". But the plan forces the ownership verifier to run `npm prefix --global` and `npm root --global` at least twice per tool using `environment.raw`, i.e. against the user's real `~/.npm`, which writes `_logs` entries and the `_update-notifier-last-checked` sentinel. The planner's own `view.json` shows the update notifier firing, so this is not hypothetical. AC09 cannot catch it because that row runs with a synthetic HOME. Either the sentence is false or the implementation must diverge from what the brief says to "retain".

**Concrete fix.** Decide and state one of: (a) extend the scratch cache/log override to **all** npm invocations in this flow, which requires injecting the per-invocation environment into the ownership probe — allowed, both `NpmOwnershipProbe.swift` and `InstallationOwnershipVerifier.swift` are on the modify list, but it changes M9-accepted verification behavior and needs an `InstallationOwnershipTests` regression and an explicit "this changes M9 npm query environment" note; or (b) keep M9 behavior and reword B02.5 to "config/metadata invocations never access the shared `.npm` cache; the retained M9 ownership queries keep their accepted environment (a known shared-cache touch, unchanged from M9)", with an AC09 row that *measures* the touch rather than asserting its absence.

### 5. B03.2/AC04 require rejecting "duplicate relevant keys", which the codebase's JSON path cannot observe
**Locations:** brief B03.2 and AC04 ("fake … duplicate …"); code: no duplicate-detecting JSON helper exists — every parse in Core uses `JSONSerialization`/`JSONDecoder` (`HomebrewUpdateProbe.swift:290`, `NpmOwnershipProbe.swift:467`, `DetectorRegistry.swift:752`), both of which are silently last-wins.

**Problem.** The measured npm shape has three fixed keys whose *names* npm itself emits (`name`, `version`, `dist-tags.latest`); registry-controlled data appears only as values. A duplicate key can therefore only come from a hostile `npm` on PATH, and it is not observable through Foundation's parsers. As written the worker must either hand-roll a JSON tokenizer in a safety-critical metadata path (new risk, no existing precedent, and "no permissive parsing" gives it no room to be lenient) or quietly fail AC04.

**Concrete fix.** Either (a) drop the duplicate-key clause and replace it with what is actually enforceable and sufficient — strict single-object, exact three-key set with no extras, `String`-only values, name equality against the verified package, `version` == `dist-tags.latest` under strict SemVer, no nested `dist-tags` object, 1 MiB cap — and amend AC04's "duplicate" case to a *duplicate-object* / extra-key / nested-shape case; or (b) keep it and specify the exact detection mechanism (a `@testable`-visible three-key flat-object scanner with its own malformed/oversize/duplicate fixtures) as a named deliverable of `NpmUpdateProbe.swift`.
