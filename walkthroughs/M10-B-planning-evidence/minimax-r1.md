## Material findings (blocking — brief must be revised to R2)

### F-1 The proof-carrying seam does not exist and is not specified (blocks B01.3, B02.4, B04.2, B04.5, AC02, AC06, and M10-C continuity)

- Brief: `briefs/M10-B-npm-latest.md:36` (B01.3 "Reuse the ownership verifier's complete proof"), `:44` (B02.4 "reverify full ownership"), `:58` (B04.2 "proof fingerprint covering manifest/bin/root identities"), `:61` (B04.5), `:75` (file authority).
- Code: `Sources/AgentLensCore/Ownership/NpmOwnershipProbe.swift:48-102` defines `private struct NpmProof` holding exactly the identities B04.2 needs (prefix, root, package, prefixBin, manifest `FileIdentity`, bin, managerBin, plus lexical paths) and a `revalidate()` returning `InstallationOwnershipReason?`. But `:206` returns `.verified(match.0)` — **the proof is built and discarded**. `Sources/AgentLensCore/Ownership/InstallationOwnership.swift:28-59` (`VerifiedInstallation`) therefore carries manager, packageName, manager entry/target/fingerprint, `managerRoot` (prefix), `installationRoot` and `selection` — but **no manifest or bin identity**. `Sources/AgentLensCore/Ownership/InstallationOwnershipVerifier.swift:114-137` (`private static func verifyNpm`) and `:166-188` (`private static func resolveNpm`) are both private, so B02.1's "resolve the manager … using the existing verifier" has no reachable seam either.
- Constraint that shapes the fix: `ObservedExecutable`, `FileIdentity`, `DirectoryIdentity` are **module-internal** (`Sources/AgentLensCore/Process/ExecutableIdentity.swift:28,35,48`) while `ExecutableFingerprint` is public (`:16`); Swift cannot expose internal types in a public API. `VerifiedInstallation.init` is deliberately internal (`InstallationOwnership.swift:40`) — that is the existing "no public forgeable token" pattern to copy.
- **Fix (name it in the brief):** specify an AgentLensCore-internal seam, e.g. `NpmOwnershipProof` (internal struct) carrying the manifest/bin/root identities plus `revalidate() -> InstallationOwnershipReason?`, returned alongside the outcome by an internal `verifyWithProof(...)` in `InstallationOwnershipVerifier.swift`, plus an internal `resolveNpmManager(...)` accessor; the npm cache key then hashes the proof's identity fields. State that no public type changes, so M9's public surface and its existing tests stay valid.

### F-2 B03.4's typed-unknown list contradicts the stdout-only runner (unimplementable inside the allow-list)

- Brief `:53`: "Output overflow, timeout, offline, authorization/rate-limit, malformed/unavailable metadata are typed unknowns. Do not guess network/rate-limit from opaque exit codes; generic failure stays probeFailed." The two halves are mutually exclusive as written.
- Code: `Sources/AgentLensCore/Updates/ProcessUpdateCommandRunner.swift:1-7` states the production bridge "cannot distinguish DNS or HTTP 429 from other failures, so those map to probeFailed (never guessed)"; `:40-51` returns stdout only. The seam `UpdateCommandRunner.run(...) -> CommandOutcome` (`Sources/AgentLensCore/Updates/HomebrewUpdateProbe.swift:104-111`) carries `Result<Data, CommandFailure>` — **stdout only, no stderr**; `CommandFailure` (`:87-99`) even comments that `networkUnavailable`/`rateLimited` "require typed evidence from an adapter". `Sources/AgentLensCore/Process/BoundedProcessRunner.swift:4-14,24-30` captures exactly **one** stream (the other is discarded) and caps stdout at 1 MiB — so capturing stderr would require editing `BoundedProcessRunner.swift` **and** `ProcessUpdateCommandRunner.swift`, neither of which is in the allow-list (`:73-81`), and would risk the credential-bearing output B02.6 forbids recording.
- **Fix:** split the sentence. "Typed npm metadata unknowns: output overflow, timeout, malformed/unavailable metadata, cancellation. Offline, authorization and rate-limit are **not** distinguishable through the stdout-only seam and therefore remain the generic `probeFailed` with the raw exit status recorded — never guessed." (Alternative: add both files to the allow-list *and* specify a stderr redaction rule. Not recommended — larger, and it widens the secret-capture surface B02.6 closes.)

### F-3 "Reverify full ownership", the per-tool query budget, and the budget-exhaustion outcome are unspecified (blocks AC07 "over-budget")

- Brief `:44` (B02.4), `:53` (B03.4 "aggregate 60-second monotonic budget per selected tool including final revalidation; do not start a step without remaining budget"), `:61` (B04.5), `:97` (AC07 "over-budget").
- Two readings exist and they are not equivalent: (a) re-run the full ownership verifier — 2 more manager queries (`npm prefix --global`, `npm root --global`) plus the anchored manifest re-read; or (b) re-observe the recorded proof identities only (no queries). Reading (a) yields up to **9 npm invocations per selected tool**: 2 ownership + 1–2 registry + 1 metadata (≤20 s) + 1–2 registry re-read + 2 ownership re-read; worst case ≈ 8 × 3 s + 20 s ≈ 44 s against the 60 s budget, before spawn overhead — and the final re-read happens *after* the metadata call, so the budget can be exhausted exactly at the publication step. The brief names no outcome for exhaustion (unknown reason? no cache write? no publication?), so AC07's over-budget row has no defined expected observable.
- **Fix:** state the mechanism explicitly (recommend (a) — it is what "full ownership" says and it detects a moved install root), give the explicit budget (≤ 9 npm invocations; ≤ 3 s per config/ownership process; ≤ 20 s for the single metadata process; 60 s aggregate per selected tool), and define the exhaustion outcome: typed unknown, **no** cache write, **no** publication, no partial result.

### F-4 B02.5's invocation-local npm cache/log recipe is neither named nor demonstrated (blocks AC09 and the phase's central safety envelope)

- Brief `:45` (B02.5 "Every config/metadata invocation uses a unique app-owned temporary npm cache/log root, mode 0700 … override npm cache/log settings only for that invocation"), `:50` (B03.1 "plus invocation-local scratch cache/log flags"), `:107` ("Freeze exact command/native fixture recipe before dispatch rather than asking worker to invent safety acceptance").
- The cited evidence does not cover it: `/private/tmp/agent-lens-m10b-plan-b7klgulu/view.json` records an argv with **no** `--cache` and no log flag (`["view","@openai/codex@latest","name","version","dist-tags.latest","--json","--global","--registry","https://registry.npmjs.org/","--prefer-online","--offline","false","--fetch-retries","0"]`), and the run used one shared synthetic `cache/` root, not per-invocation unique roots. The npm debug log confirms the argv (`cache/_logs/2026-10-27T11_22_54_439Z-debug-0.log:7`) and confirms where npm 10.9.8 writes logs: `logfile logs-max:10 dir:/private/tmp/agent-lens-m10b-plan-b7klgulu/cache/_logs/…` (`:8-9`) — i.e. `_logs` lives **under the cache root**, so a per-invocation `--cache=<owned root>` relocates both the transport cache and the logs on this npm. No `logs-dir` config appears in the measured logs.
- **Fix:** name the override concretely (`--cache=<unique app-owned temp root>` per invocation, root created 0700, removed afterwards; `_logs` follows the cache root on npm 10.9.8), and require the preparation proof to record: (a) npm 10.9.8 accepts the flag; (b) a sentinel placed in the real `~/.npm` is untouched after a config **and** a metadata invocation; (c) the root is 0700 and removed; (d) both `npm config get` invocations (which also emit `_logs`) use the same per-invocation rule.

### F-6 The npm temp-root / registry-transport injection seam is unspecified, so AC08/AC09 are not executable as written

- Brief `:98` (AC08 "controlled native host compiling unchanged final product views with injected service"), `:99` (AC09 "controlled registry transport"), `:105` (Preparation: "controlled local registry endpoints are test-only injected seams").

## Verified-correct points (no change requested; recorded so the brief is not "fixed" in the wrong direction)

## Strongest objection (non-blocking, but should be answered in R2)

**The phase is specified against npm v11 documentation while the only npm present is 10.9.8, and nothing in the product pins or records the npm version it actually ran against.** Every behaviour the phase leans on was confirmed here from npm 10.9.8's *installed source* and the coordinator's npm-10.9.8 measurement — global-mode project exclusion, effective-merged `config get`, `pickRegistry` scope precedence, `--prefer-online` ⇒ `no-cache`, `_logs` under the cache root — and all of them happen to be favourable to the brief. But the user's npm at runtime is whatever they have (the measured stderr announces 10.9.8 → 12.2.1, i.e. two majors behind current), and `npm view <pkg>@latest name version dist-tags.latest --json` may change shape across major lines (nested `dist-tags`, different field handling). The brief's fail-closed rule (`:51` "if this shape cannot yield one unambiguous package/version/tag object, stop with evidence for a revised brief, not permissive parsing") keeps the *safety* intact — a different npm yields a typed unknown, never a wrong number — but it means users on other npm versions may see a permanent neutral unknown with no explanation, and the brief currently neither measures a second npm line nor records the npm version as part of the observation. **Recommendation (non-blocking):** require the npm metadata observation to record the npm version it ran against (non-secret), state explicitly that the accepted JSON shape is verified only for the measured version and that every other version fails closed to a typed unknown, and have the preparation measure one additional npm major line if a worker can obtain one without installing anything into the product. This keeps the phase honest about what it knows rather than assuming v11 semantics for every user.
