## 3. Residual precision items — non-blocking, each a one-line freeze-time edit

1. **Base-custom + scope-public eligibility is ambiguous (safety-adjacent).** B02.3 says a "configured custom/private registry is unknown/unsupported", while B02.4 binds `--registry=<accepted>` *and* `--@scope:registry=<accepted>`. If the base is custom and the scope is public, Reading A (base custom ⇒ refuse) is the only one consistent with "Do not override a custom setting with public registry to make eligibility pass"; Reading B (scope wins ⇒ proceed) contradicts it. AC03 lists exactly this case ("base custom + scope public") without naming the observable. **Recommend one sentence:** *eligibility requires the effective base registry **and**, for a scoped verified package, the effective scope registry to each be the accepted public origin or unset; any custom/malformed value in either refuses with zero metadata requests.*
2. **Scratch-root granularity.** B02.5 says "unique … per invocation" and "override … only for that invocation", but `InstallationOwnershipVerifier.verify` takes one `environment` for both `prefix` and `root` queries — so the strict per-*process* reading needs a per-query env hook inside `NpmOwnershipProbe`, which the file-authority clause ("solely to expose/revalidate npm proof") does not obviously cover. **Recommend naming the granularity** (e.g. one owned root per ownership verification / per registry-or-metadata invocation, never shared across groups) so the worker is not stopped mid-implementation by the brief's own "need beyond allow-list" rule. Isolation is safe under either reading.
3. **The clipped runner must reach the ownership queries.** B03.4 places the clipping wrapper "in the coordinator"; it must also be the `runner` passed into the ownership verification inside the update stage, or a 10 s ownership query can overrun the 60 s stage budget by up to one step (bounded, and still under the 120 s CLI watchdog). **Recommend one clause:** the same clipped runner and the same derived scratch environment are passed to `verifyWithProof(...)` for the initial and final ownership passes.
4. **`npm --version` failure semantics.** B05.1's "malformed/unavailable version is unknown" reads both as "the observed npm version is unknown" and as "the tool status becomes unknown". The conservative reading is safe but needlessly suppresses a strictly-parsed comparison. **Recommend:** an unavailable npm version makes the provenance's npm version unknown and is recorded as such; it does not by itself invalidate an otherwise strictly-parsed metadata comparison (the shape contract is what decides).
5. **The recorded populated-config probe has no env-layer case.** `registry-probe.py:17` deliberately strips every `npm_config_*` variable, so the receipts cover the user and project file layers but not an inherited env-level `npm_config_registry` / `npm_config_@scope:registry` — yet B02.5 preserves those and AC03 names "env". The env layer sits *above* the user file layer in npm's chain, so it is the more likely way a custom registry arrives. **Recommend adding one env case to the pre-dispatch populated-config probe** (no code change needed).

## 4. Strongest objection (not a blocker; should be answered in the freeze text)

**The six-hour reuse promise is contingent on a validation chain that the phase itself mandates, and the brief nowhere bounds or orders that chain against the budget it just imposed.** Per npm subject, R2 mandates 8 npm process launches even on a cache *hit* — 2 initial ownership (`prefix`/`root`), 2 initial registry reads, 2 registry re-reads, 2 final ownership — plus the metadata `view` on a miss; with the two npm tools in the shipped registry (`codex` → `@openai/codex`, `opencode` → three npm candidates) that is ~18–19 launches per Check, of which the six-hour cache saves exactly **one** (the metadata view). And because B04.4 places the cache lookup *after* ownership+registry validation while B02.4 places the final re-validation *after* the lookup, a budget exhaustion at either point yields `budgetExhausted` — **not** the cached status the "User outcome" section promises ("Check can reuse valid six-hour npm metadata"). With nominal bounds of 10 s (ownership) and 3 s (config), a slow-but-healthy npm can exhaust the 60 s stage budget on a *cache hit* and show a neutral unknown for a record that is sitting on disk, valid and unexpired.

R2's own words license this ("This intentionally permits budget-exhausted unknown even if every individual step could have succeeded given its full nominal timeout"), and the degradation is honest and typed, so this is not a defect. But it is the gap a user will feel first, and it is fixable in the brief rather than in the code. **Two cheap options for the freeze text:** (a) state the degradation order explicitly — *"a budget-exhausted Check reports `budgetExhausted`, never the cached value; the cached record remains on disk and is reused by the next Check that completes validation within budget"* — and state the expected number of npm invocations per subject, so AC06's "distinct scratch roots hit the same record" is falsifiable against a stated cost; or (b) hoist the per-manager `prefix`/`root` query to once per manager per stage (the proof for a given manager/prefix/root is identical for every subject sharing it) and keep only the per-subject manifest/bin/selection re-check — which cuts the per-subject process cost roughly in half and materially improves the chance that the promised cache reuse is reachable inside 60 s. I recommend (a) unconditionally and (b) if the coordinator wants the reuse promise to be real rather than merely permitted.
