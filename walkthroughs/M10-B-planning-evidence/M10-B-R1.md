## Research and inspected seams

Primary sources inspected 2026-10-27:

- [npm view](https://docs.npmjs.com/cli/v11/commands/npm-view/): named metadata fields and JSON output; explicitly request `@latest`, not the configurable default tag.
- [npm dist-tag](https://docs.npmjs.com/cli/v11/commands/npm-dist-tag/): `latest` is a publisher-managed tag, not necessarily the largest published version; beta/next have no automatic stable-channel meaning.
- [npm config](https://docs.npmjs.com/cli/v11/using-npm/config/): online/offline cache policies and registry settings. A fresh empty npm transport cache is required for Refresh; `prefer-online` alone does not establish an uncached network observation.
- [npmrc](https://docs.npmjs.com/cli/v11/configuring-npm/npmrc/): scope registry overrides and user/global configuration. Never dump configuration/authentication or parse `.npmrc` wholesale.

Current code: `NpmOwnershipProbe` verifies manager, prefix, global root, package manifest/bin and selected executable with bounded descriptor-anchored reads and final revalidation. `VerifiedInstallation` is invocation evidence, not a durable permission token. It currently lacks registry identity and installed manifest version. `UpdateProbeSubject` currently carries no detector definition; `ToolUpdateResult`, coordinator, cache and provenance rendering assume Homebrew. `InventoryService.applyingUpdates` and CLI construct subjects; the app publishes local facts before checking, with one pipeline and generation/cancellation guards. Extend those actual seams, retaining Homebrew behavior, rather than adding a parallel CLI/UI engine.

## Behavioral contract

### B01 — modes, association and local facts

1. Plain scan, offline scan, app launch and local rescan remain zero manager-query, zero update-cache read/write and zero metadata network operations. Existing bounded local tool version measurement is unchanged. Explicit Check/Refresh authorize read-only ownership/config queries for npm, without requiring a previous Verify Installation click.
2. Carry the validated `DetectorDefinition` into each update subject; retain stable registry ID, selected entry/canonical target and current local version together. Reject inconsistent definition/ID/selection before manager/network work. Never use a display name, filename or completion order as association. Migrate all production and test constructors directly, without deprecated overloads.
3. Only the selected npm installation receives a status; aliases/shadowed/off-PATH facts remain accurate. A declaration/source hint alone is insufficient. Reuse the ownership verifier's complete proof. No match, multiple match, absent manager, unsafe manifest or any changed proof yields neutral unknown and no metadata publication/cache write.
4. Compare the local version attached to that exact diagnostic selection. Missing/unparseable local version stays unknown; do not borrow a shadowed/winner version or run the selected tool again just to fill metadata. If installed manifest version is used for consistency, it must be read through the existing anchored proof and cannot replace selected diagnostic version silently.

### B02 — registry and command context

1. Resolve the manager from the captured session environment using the existing verifier. All commands use its verified absolute executable path and literal argument arrays, never a shell string. Use npm global mode consistently, so project `.npmrc` cannot choose the registry for a global installation.
2. Query only `npm config get registry --global` and, for a scoped verified package, `npm config get @scope:registry --global`. An unset scope (`undefined`/`null` as measured for supported npm) falls back to base; failed/malformed/ambiguous values refuse. Resolve only the verified package's scope, never every declared alternative.
3. This slice supports only normalized `https://registry.npmjs.org/` (optional trailing slash), with no credentials, query, fragment, alternate port or path. A configured custom/private registry is unknown/unsupported with zero public fallback and no metadata request. The URL is current effective lookup routing, not proof of where a historical installation was downloaded. UI/records must not claim historical origin was proved.
4. Do not override a custom setting with public registry to make eligibility pass. Bind the accepted registry into the metadata command explicitly after checking it. Re-read effective registry and reverify full ownership after the query/cache lookup, immediately before publication/persistence. Manager, package, prefix/root, manifest/bin/selection and registry must match the initial observation. A change or cancellation discards results.
5. npm may write its transport cache/logs even for read-only commands. Every config/metadata invocation uses a unique app-owned temporary npm cache/log root, mode0700, outside personal npm cache and install roots; override npm cache/log settings only for that invocation. No shared `.npm` content access, cleanup or npm config write. Clean up only owned children after bounded child-process shutdown. Use the same environment/global-config context for initial/final checks. Never record credential-bearing output/URLs; classify narrow parsed errors and keep raw fixture receipts secret-free.
6. Preserve configured auth/registry behavior for config resolution; do not read/log tokens. Metadata request targets only the accepted public host. No interactive login, token provisioning, sudo, lifecycle scripts, npm install/update/uninstall or global settings changes.

### B03 — latest metadata and limits

1. Proposed measured command shape (absolute manager + array): `view <verified-name>@latest name version dist-tags.latest --json --global --registry=https://registry.npmjs.org/ --prefer-online --offline=false --fetch-retries=0`, plus invocation-local scratch cache/log flags. Planning probe on npm10.9.8 succeeded: one object with string keys `name`, `version`, and literal dotted key `dist-tags.latest` (not a nested object). Parse that measured shape strictly; verify the worker npm version and shape before dispatch; if this shape cannot yield one unambiguous package/version/tag object, stop with evidence for a revised brief, not permissive parsing. No request ranges, git/file/tarball specifiers or arbitrary package names; package names come from validated matched declarations.
2. Accept exactly one bounded JSON object naming the exact verified package, with a strict SemVer `version` equal to `dist-tags.latest`. Reject empty/multiple objects, name mismatch, wrong types, duplicate relevant keys, malformed JSON, missing tag/version, banners on stdout and truncation. Do not use npm `wanted`, `outdated`, max-version sorting, beta/next or the configured tag. npm's real JSON shape is a planning prerequisite, not a worker guess.
3. Reuse strict semantic-version ordering, including prereleases and build metadata; do not loosen Homebrew parsing. Stable latest versus older installed prerelease compares by SemVer. Installed ahead of tag stays unknown/newer-than-known, with no downgrade suggestion. If `latest` itself is a prerelease, show neutral unsupported-channel unknown rather than recommending an unstable update; no inference of the user's channel.
4. Per config/ownership process retain existing bounded runner limits (at most3 seconds, 1MiB output); metadata process maximum20 seconds, captured stdout maximum1MiB (existing runner discards stderr; do not claim a combined-stream cap), retries0. One metadata process at a time; cancellation suppresses subsequent steps/publication and waits for the active bounded runner to return/clean its process group; existing runner does not provide immediate cooperative termination. Do not promise immediate shutdown. Enforce an aggregate60-second monotonic budget per selected tool including final revalidation; do not start a step without remaining budget. Process cleanup may extend wall time; report that limit honestly. Output overflow, timeout, offline, authorization/rate-limit, malformed/unavailable metadata are typed unknowns. Do not guess network/rate-limit from opaque exit codes; generic failure stays probeFailed.

### B04 — npm cache

1. Keep Homebrew schema3/cache semantics intact. Add a separate bounded npm metadata document beside the injected Homebrew cache: `npm-update-metadata-v1.json`, schema1, maximum1MiB, atomic replacement, injected clock/URL for tests. Never derive it from real HOME in tests. No generic cache migration framework or reading old npm schemas.
2. Key includes registry ID, verified npm package, normalized registry and tag `latest`, observed manager entry/target/fingerprint, verified prefix and installation root, selected entry/target/fingerprint, proof fingerprint covering manifest/bin/root identities, and a stable digest of effective non-secret query context. No raw environment/auth or full unrelated package inventory. Prefix is not interchangeable with npm root. A new prefix/manifest/manager/registry invalidates a hit.
3. Persist validated stable metadata and observation time, never final comparison status or failed/unsupported results. Recompute against current local version after fresh ownership/registry validation. TTL is `0 <= now-observedAt < 6h`; exactly6h/expired/future is a miss. Preserve original observation time on hit. Corrupt/oversize/ambiguous cache is a miss, not a scan failure. Writes cannot change Homebrew records.
4. Check uses a matching live validated entry without a metadata `view` call, but still performs bounded ownership and registry validation. Refresh bypasses Agent Lens cache and uses a fresh empty npm transport cache (no stale fallback), then replaces the applicable record only on success. Failed Refresh shows unknown, not the old badge; prior valid disk metadata may remain until expiry but is not used by that Refresh. Plain/offline never read either metadata document.
5. Revalidate cancellation/identity immediately before committing a record/publication. Do not claim this eliminates every filesystem race or provides an atomic transaction; an observed changed identity must fail closed.

Dynamic strings render as plain text; timestamps mean observation time, not release time. Generalize manager-specific unknown wording accurately. Unknown never increments update count.
3. Preserve one app pipeline, local-first publication, conflicting-action coalescing and generation ownership. Check/Refresh/rescan/selection changes/window closure/cancellation cannot publish stale status or leave an unjoined process. Unsupported manager remains usable local inventory; no new operation buttons or automatic requests.
