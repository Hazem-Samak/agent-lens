## Blocking findings

1. **§4-D05.2** — Removal predicate contradicts itself. The bullet defines "removed" as the package directory "no longer has the recorded directory identity," but the same paragraph says a directory "replaced by a different identity … is not proof of clean removal." Concrete failure: npm exits 0, `proof.packageLexicalPath` is re-populated by a different installation (harness decoy or partial rewrite) with the bin link gone — a literal bullet-1 implementation returns `.succeeded`/delta "identity gone," while the clarifier and D05.3 ("exit 0 with the package … still present is `.uncertain`") demand refusal; AC05/AC06 then pass or fail depending on which sentence the implementer tests.

2. **§4-D04.3/D04.4 vs D05.3** — No precedence rule between interruption and "nonzero exit is `.failed`." A cancelled or timed-out run can still end with a nonzero status (npm may trap SIGTERM and exit 143; SIGKILL deaths are recorded as nonzero signal status). Concrete failure: user cancels mid-uninstall, npm exits 143, D05.3 classifies it `.failed` with "npm refused the removal" implication, directly violating D04.4/AC08's "after launch … `.interrupted` or `.uncertain`" and printing a false factual failure message.

3. **§4-D03.1 + §6-AC04** — Compare-every-bound-field including "proof fingerprint" and environment, but the brief never pins that a fresh proof's fingerprint is recomputed over deterministic canonical facts. Concrete failure: if the fingerprint embeds anything volatile (scan timestamps, attempt ordinals, per-run scratch evidence), every confirmation refuses unconditionally and AC05/AC10/AC11 can never yield `.succeeded`; conversely, without an enumerated compared-field list, AC04's environment/operation-root mutation may not actually be caught at confirmation.

4. **§4-D03.2** — The "immediately before launch, revalidate the live proof and owned operation root again" step is underdefined: it is distinct from the D03.1 revalidation yet has no budget (D04.2 defines only two 60-second read-only budgets), no failure mapping, and no statement of what "revalidate the live proof" means. Concrete failure: implementation treats D03.1's pass as satisfying it, so a selection/operation-root change in the final pre-spawn window reaches mutation (AC04's window case missed); or a full third verification chain runs with no deadline while holding the exclusive `OperationExecutionGate`, breaching the D04.2 budget scheme.
